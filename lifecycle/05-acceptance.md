# Phase 5 · acceptance（验收闭环）

> **发版完成的定义：acceptance 闭环结束，而不是部署命令跑完。**

## 目标

以**本次发布的内容**为输入，组织定向功能验收，形成可追溯的验收报告。验收是 memory 的前置闸门：验收未闭环，禁止记 ledger 终态、禁止同步 memory、禁止对用户宣称"发版完成"。

## 前置条件

- health 已通过
- 已有"本次发布内容摘要"（来自 release 阶段：发了什么功能/改动/修复）
- 可选：大版本的 `plans/<项目>/*-release-plan.md`（含验收标准）

## 操作手册（六步）

1. **列变更清单**：本次改了哪些功能点/接口/页面？
   - backend 线索：发版前 preflight 的 rsync 差异清单；或 `git log` 本地变更
   - frontend 线索：本次构建包含的功能改动；feature markers
2. **推导测试项**：每个变更点至少一条**线上**验证项；重点接口加正向+异常两条。不是全量回归，只测"这次发了什么"+ 受影响路径
   - **前端 SPA 最低验收标准**：必须核对**页面实际加载的入口**引用的是本次构建产物——对比 `index.html` 中引用的 chunk 哈希文件名与本次 `dist/assets/` 产物一致。"新文件在云端 dist 里"≠"页面会加载它"（旧 index.html / 浏览器缓存场景真实存在，2026-11-03 列布局发版实录：只验了文件存在，未验引用关系）
   - **视觉类变更**（布局/列宽/样式）：文件级验收之上，至少让用户在真机/浏览器确认效果，或截图比对；"样式类已包含"不是视觉验收
3. **执行验收**：
   ```bash
   # 页面可达与关键内容
   curl -s <站点URL> | grep -q '<关键内容>' && echo PASS || echo FAIL
   # API 行为（按变更点选端点）
   curl -s -X POST <API> -H 'Content-Type: application/json' -d '<最小用例>'
   # 前端功能标记线上复核（对照 01-preflight 的清单）
   ssh <server> "grep -rls -e '<marker>' <远端assets目录> | head -1"
   ```
4. **浏览器端到端实测（E2E_MODE 控制档位，规程见 `references/browser-e2e.md`）**：
   - **第 0 步·能力前置检查**：按宿主自检浏览器能力（WorkBuddy 内置浏览器 / Claude·Codex 的 playwright MCP）；**缺失时不得静默跳过、不得标 ✅**——报告用户二选一：授权安装后补验，或明确接受文件级放行（台账记"部分验证（无浏览器 E2E）"）
   - 流程：打开目标 URL → 逐条验证变更点 → **整页截图存 `evidence/<项目>/gateo-<发版目录>/`（路径进台账"证据"列）** → 强刷复验（防加载旧 chunk）→ 角色差异用对应账号各验
   - 档位：`auto`（前端必做/后端影响页面才做，推荐）/ `always` / `off`（如实记"部分验证"）
5. **生成验收报告**（表格模板；**每次发版都存** `evidence/<项目>/gateo-<日期>_<TS>_<目标>/gateo-acceptance-report.md`，结论摘要追加到 ledger 验收列）：

   ```markdown
   ## 验收报告 <日期> <项目> <目标>
   | # | 测试项 | 预期 | 实际 | 结论 | 证据 |
   |---|---|---|---|---|---|
   | 1 | SSO 登录跳转 | 302 到 sso/exchange | 同左 | ✅ | curl 输出摘要 |
   ```

6. **闭环判定**：全部 ✅ → 进 ledger（结果=成功，验收=通过）；任一关键项 ❌ → 走 rollback 分支，ledger 记"验收未过回滚"，非关键缺陷可放行但必须在台账备注并告知用户

### 生产数据验收纪律（2026-11-03 实录教训）

验收常需在生产库造/改测试数据（如把某题设为"必修"再改回）。严守以下四条：

1. **先取 before 值再动手**：改任何生产数据前，先读出并记录原值（SELECT/GET），
   清理时恢复到这个真实值，而不是记忆里的值。
2. **清理不得依赖假设的路由**：先确认接口真实存在且 HTTP 方法正确——405 = 方法不对，
   不是成功；不确定时优先用与造数**相同的通道**清理。
3. **无法安全清理的用例直接跳过**：宁选 skip-path（只读验收），不在生产库留脏数据；
   实录中清理逻辑曾因假设了不存在的 GET 路由（405）而整体未执行。
4. **恢复失败必须立即告警**：验收产生的数据残留要如实报告用户并给出手工清理
   SQL/步骤，不得静默。

## 失败处置

- 关键项失败 → 视同发版失败 → `rollback.sh` → 回滚后对"恢复结果"**重新做一次最小验收**（证明回到的版本是好的）→ ledger 记录
- 无法线上验证的项 → 如实标注"未验证"，不得标 ✅

## 输出物

- 验收报告（`evidence/<项目>/gateo-<发版目录>/gateo-acceptance-report.md` + 台账验收列结论）
- 浏览器 E2E 截图（`{项目工作区}/deploy-evidence/`，路径记入台账备注）
- 明确的闭环结论：通过 / 部分验证（附原因）/ 回滚 / 带瑕疵放行（附说明）

## Agent 检查点

- [ ] 测试项必须来自本次变更，不是套模板
- [ ] 每条结论都有证据（命令输出），无证据不得标 PASS
- [ ] 浏览器 E2E：能力已前置检查（缺失未静默跳过）、截图已留存且路径入台账
- [ ] 涉及生产数据写入的用例：before 值已记录、清理通道已验证、残留已零确认
- [ ] 验收未闭环前，不得写 memory、不得报"完成"
