# Phase 6 · rollback（回滚，异常分支）

## 目标

把服务恢复到最近（或指定）回滚基准，并**对恢复结果重新验收**。原则：能上线不算完，能回滚才算稳。

## 前置条件

- 触发条件（任一）：health 失败 / acceptance 关键项失败 / 用户主动要求
- 已知回滚基准（backup 阶段记录的文件名；不指定则自动取最近一份）

## 操作手册

```bash
PROJECT=<名> bash scripts/rollback.sh list                 # 列出云端备份（最新在前）
PROJECT=<名> bash scripts/rollback.sh backend [备份文件名]  # 后端：构建源+容器+重启+健康检查
PROJECT=<名> bash scripts/rollback.sh frontend <admin|h5> [备份文件名]
```

- backend 回滚链路（v3.1 起精确快照：先清空目标目录再解包，不留新版本残留文件）：构建源恢复 → 容器先清后灌 → 重启 → 自动健康检查
- frontend 回滚（v3.1 起精确快照）：先清空站点目录再解包，恢复到与备份完全一致的状态；不再有旧 hash 残留
- **备份命名双兼容**：`gateo_backend_app_bak_*`（新命名，2026-11-03 起）/ `backend_app_bak_*`（历史备份）均可回滚，类型自动判定按 `*backend_app_bak_*` / `*backend_src_bak_*` 子串匹配——历史备份不需要迁移

## 失败处置

| 情形 | 处置 |
|---|---|
| 回滚后健康检查未过 | 打印容器日志排查；考虑换更早一份备份重试 |
| 无可用新格式备份 | 需用户确认后使用旧格式历史备份（手动指定文件名） |
| 回滚也失败 | 升级为事故：完整保存现场（容器日志、备份列表、报错输出），报告用户 |

## 输出物

- 回滚完成 + 健康检查结果
- **恢复结果的最小验收结论**（关键功能可用性确认，参照 05-acceptance 简化执行）

## Agent 检查点

- [ ] 回滚后必须重新验收，"恢复命令成功" ≠ "服务恢复正常"
- [ ] 回滚也是一次发版事件：必须走 ledger → memory（结果=回滚，附原因）
- [ ] 回滚前向用户报告要恢复到哪个备份文件
