# Hotfix 剧本（线上故障 / 业务 bug 的前向修复）

> 借鉴 spec-kit 的 bug fixing 流程：**assessed cause → scoped fix → recorded verification**。
> 与八阶段发版衔接但入口独立；适用场景：线上行为错误、数据口径错误、接口 500/405 等"服务活着但结果不对"的问题。

## 第 0 步 · 甄别：这真的是 hotfix 吗？

先用铁律 6 的甄别思路分三路：

| 现象 | 处置 | 走哪个剧本 |
|---|---|---|
| 服务起不来 / 探活持续失败 | 立即回滚到最近备份 | `rollback.md`，修好再重发 |
| 服务活着但行为/数据错误 | 本剧本（前向修复） | hotfix |
| 疑似配置/环境问题（非代码） | 只读诊断，报用户 | 不改代码，先诊断 |

**用户确认闸门**：修复方向（紧急回滚 vs 前向修复 vs 先诊断）必须报用户裁定，不得自行选择"不回滚、转修复"。

## 第 1 步 · 根因评估（assessed cause）

- 复现路径 + 最小证据（日志片段 / 请求响应 / 数据快照），写清"错误行为 vs 期望行为"
- 根因定位到**文件与函数级**；跨层问题前后端一起排查，不单信单层
- 评估**影响面**：哪些用户/数据已被错误行为污染？（决定是否需要 data-change.md 做数据订正）
- 根因结论报给用户，附修复方案草案

## 第 2 步 · 范围化修复（scoped fix）

- 修复 = **最小变更**：只动根因文件，禁止顺手重构、禁止捎带其他改动（混入的改动会污染差异归属）
- 改动前确认本地源码已 git 管理（铁律 3 前提）；本次修复单独 commit，注明根因
- 发版走标准链路：`gateo-plan` → 用户确认计划 ID → `gateo-apply`——hotfix **没有发版快车道**，计划闸门同样生效
- 数据订正（如有）走 `data-change.md`：`gateo_data_*` 备份 → 引用检查 → 变更

## 第 3 步 · 验证留痕（recorded verification）

- 验收必须包含**根因对照验证**：修复前复现路径重放，证明错误行为消失、期望行为出现
- 回归检查：修复是否波及其他路径（同函数/同接口的其他调用方）
- 台账行备注必须写：根因一句话 + 修复范围 + 验证证据；证据目录存诊断与验收产物
- 收尾按 SKILL.md"发版后记忆写入"执行，不可跳过
