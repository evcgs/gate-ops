# 过程剧本 · publish（对外发布 / 开源发布）

> 触发词：开源发布、发到 GitHub、上线官网、发公众号、对外发布、脱敏导出。
> 本剧本 v3.3.0 起，源自 2026-11-04 gate-ops 首次开源发布的真实泄漏事故（详见下方教训表）。
> **核心认知：对外发布（GitHub/官网/公众号/交付物）本质是一次发版**——目标仓库是"生产环境"，脱敏是"数据安全"，发布后复审是"验收探活"。release 剧本的所有纪律在此全部适用。

## 教训 → 闸门对照表（每条都是真实事故）

| 事故 | 闸门 |
|---|---|
| CHANGELOG/references 的"真实案例"列带真实系统名（10+ 处）随包发布，导出器终检没查 | 敏感词终检必须含**项目名词典 + 业务词词典**，不只查 IP/密钥/凭据 |
| 泄漏靠用户追问"没带敏感信息吧"才发现——发布即终点，没有复审 | **发布后独立复审**是强制终点步骤：隔几分钟用独立宽词表复扫远端，0 命中才闭环 |
| 提交作者 QQ 邮箱进入公开历史 | 发布前**提交元数据检查**：author/committer 邮箱一律用 GitHub noreply |
| 脱敏靠临时手工 sed，规则散落对话里，下次发布复现 | **匿名化映射表是可审计产物**：以映射文件入库（谁→什么代号），导出器自动套用 |
| 本机绝对路径 `/Users/<user>/...` 混进文档 | 路径检查入终检词表：`/Users/<name>`、`/home/<name>`、盘符路径 |

## 阶段流程

### 阶段 1 · 发布对象与范围锚定（铁律 0 适用）

- 第一行复述：本次发布对象=<仓库/平台> · 发布内容=<包/文章/页面> · 依据=用户指定
- 用户确认**可见性**（Public/Private）与**署名**（用户名/组织/noreply 邮箱）后才可对外写入

### 阶段 2 · 资产盘点与白名单

- 明确**只发白名单内文件**（真源 ≠ 发布源：真源仓库留在本地，发布走导出包）
- 盘点排除清单：真实档案、真实台账、evidence、服务器拓扑、凭据文件、`.env`、feature-markers-<真实项目>.txt
- 确认发布目标的基础设施（仓库/Pages/域名）已就位或本次一并创建（创建动作须用户确认可见性）

### 阶段 3 · 匿名化映射表（可审计产物）

- 建立**映射文件**并入库（如 `references/anonymize-map.sed`）：真实项目名→代号（project-a…）、业务词→通用词（内容库→内容库、用户→用户）、表名→泛称、路径→`~/user-home`
- 映射表本身不含敏感原文的上下文（只含"谁变谁"），可随导出器入库供社区复用
- 导出器在终检前**自动套用映射**（stdin→临时文件→mv 写法，勿依赖 `sed -i`——toybox/GNU/BSD 三家语义不一，见 mac-traps）

### 阶段 4 · 敏感词终检（20 类，零命中才放行）

至少覆盖：域名 / IP / SSH 密钥名 / 私钥块 / 本机路径 / 个人邮箱 / QQ 邮箱 / 真实项目名（词典）/ 业务词（词典）/ 内部表名 / 真实人名 / CRED_<真实项目> 变量名 / 服务器端口映射 / 内部代号（data-dir 等）。
- 终检**后于匿名化**执行：匿名化后仍命中 = 未知泄漏，必须人工排查，不得静默替换放行

### 阶段 5 · 提交元数据检查

- `git log --format='%an %ae %cn %ce' | sort -u`——只允许发布用身份（noreply 邮箱）
- 历史提交含个人邮箱 → `--amend --reset-author` 或 squash 后强推（新仓库零风险；有他人的仓库禁强推）
- commit message 本身过一遍敏感词终检（message 也是发布内容）

### 阶段 6 · 发布与发布后复审（强制，不可省略）

1. 推送（网络代理间歇 502：同一命令重试 2-3 次，勿改流程）
2. **独立复审**（发布 ≠ 复审，二者必须分开执行）：用**另一份更宽的词表**直接扫远端内容（`gh api repos/<org>/<repo>/contents` 或拉取后扫描），不信任本地扫描结果
3. 复审 0 命中 → 台账行（`records/` 或发布台账）；复审命中 → 立即修复 + 强推 + 重扫，并在台账记录泄漏条目与修复

## 终点纪律（入口解耦）

- 本剧本终点 = **发布后复审通过 + 台账行**。
- 发布完成 ≠ 自动进入宣传（公众号文章、社区帖子是新的 publish 实例，需用户指令）。
- 复审发现的泄漏修复 ≠ 自动连带重构导出器；导出器加固是独立任务，须用户确认（本次因泄漏同源直接落地，属用户确认范围）。

## 与其他过程的衔接

| 衔接 | 说明 |
|---|---|
| ← onboarding | 导出器/白名单改造通常在接入过程沉淀新排除项后触发 |
| ← audit | 发布后复审本质是 audit 方法论（只读+实证）在对外场景的应用 |
| → release | 项目自身发版（如技能升级后重新发布）走本剧本，不走服务器 release |
