# 误操作场景手册（Misoperation Playbook）

> **定位**：gate-ops 全部闸门的"敌方行动图鉴"——每类容易误操作的事情、它如何发生、哪个闸门挡住它、如何自检。
> 用途：①接入新 agent/会话时的风险培训材料；②设计新闸门时的威胁模型；③事故复盘时的对照表。
> 原则：**这里没有一条是理论风险——每条都长自真实事故**（标注日期与系统的为实证）。
> 时代背景：当所有操作都变成"对 Agent 说一句话"，最大的风险面不再是手滑，而是**语义歧义、范围膨胀与留痕缺失**——A 类场景因此排在第一位。

---

## A 类 · 语义越界（一句话 → Agent 做多了）

| # | 场景 | 真实案例 | 规避闸门 |
|---|---|---|---|
| A1 | **讨论被当成执行授权**：用户本意是讨论方法/分析问题，Agent 理解为"去做"并直接发版 | 2026-11-03 project-a：本会话误执行发版（用户本意是讨论方法），生产短暂载入未验证代码 | 铁律 4：**分析/诊断/规划不构成发版授权**；发版只认"计划 ID 确认"这一种授权形式 |
| A2 | **范围膨胀**：用户说"发布"，Agent 把范围扩大（顺手改配置、捎带其他改动、全目录覆盖） | project-a 实录：整目录同步会连"已部署未提交"改动一起推云 | 计划 manifest 锁死覆盖范围（指纹校验）；确认框显示**文件级**差异清单——确认什么就覆盖什么 |
| A3 | **身份推断错误**：任务书没写系统名，Agent 凭历史记忆/文档线索自行推断目标系统 | 2026-11-04 project-b 误配：复核会话自行推断成 project-b 并执行整套流程 | 铁律 0：目标系统只能来自用户指定；记忆/台账/文档只能验证不能指派；候选零/多必须先问；开工复述身份 |
| A4 | **过程越界**：上一个过程的产出被"顺手"推进到下一个过程 | 审计回执顺手发版、回滚成功自动修复 | 入口解耦（processes/README.md）：**跨过程 = 新任务 = 需要用户指令**；audit 是只读终点 |
| A5 | **一句话误删**："把这个删了"——未确认引用关系就执行 | project-a 每日计划：直接删会让下游引用记录断引用 | 引用检查先于删除（`引用记录表` 计数=0 才动手）；顺序：备份 → 引用检查 → 删除 |

**自检命令**：发版类操作只认 `gateo-apply.sh` 的执行记录；一句话指令执行前 Agent 必须能回答"本次系统=X（依据）+ 本次范围=计划 ID"。

## B 类 · 数据毁灭（一句话 → 生产数据没了）

| # | 场景 | 真实案例 | 规避闸门 |
|---|---|---|---|
| B1 | **同步目标内含生产数据**：`rsync --delete` 把运行时数据目录整目录删除 | 2026-11-04 project-b：`data/`（生产 SQLite + 密钥）位于 RSYNC_DEST 内，首版即删库 | bind-mount 五步 checklist（config-schema.md）：列持久化路径 → 判定位置 → 移出或排除 → precheck 验证数据目录不在差异清单 → 写进档案 |
| B2 | **本地同名目录反向覆盖**：本地恰好存在同名数据目录，把旧数据/空数据盖到云端 | project-b 教训的姊妹风险：密钥文件被覆盖尤其致命 | 同 B1 checklist 第 3 步；`.env`/`data/` 全局排除 + `.dockerignore` 双保险 |
| B3 | **备份无效就覆盖**：备份命令"没报错"但归档是空/截断的 | 三重校验设计动机 | 覆盖前硬校验：`tar -tzf` 读全量流 + md5 边车复核 + 现场指纹比对，任一失败即终止发版 |
| B4 | **服务器独有文件被 --delete 误删**：只存在于服务器的配置/密钥文件不在本地树 | 2026-11-04 project-c：`docker-compose.server.yml` 与 `.env.public` 仅存服务器 | server-only 文件两条路：拷回本地入 git（配置类）/ 全局 rsync exclude（密钥类） |
| B5 | **回滚把数据一起滚掉**：回滚操作连带运行时数据卷 | project-d 待办：compose-build 回滚会连带 `data/` | 回滚剧本区分源码卷与数据卷；数据卷必须有独立 `gateo_data_*` 备份互补 |

**自检命令**：`PROJECT=x bash scripts/precheck-deploy.sh backend` 干跑——差异清单里出现任何数据目录名 = P0 红灯。

## C 类 · 状态误判（一句话 → 判断错了就动手）

| # | 场景 | 真实案例 | 规避闸门 |
|---|---|---|---|
| C1 | **部署成功假象**：代码落盘但旧进程还在跑（restart 缺失/失败） | 2026-11-03 project-a：代码已同步、进程仍跑旧码（StartedAt 早于落盘时间） | 就绪探活三层语义（liveness/readiness/acceptance）；探活响应体校验，不只看连接成功 |
| C2 | **启动预热误判为故障**：健康检查 30 秒窗口内失败即判死，实际应用要 60 秒预热 | 2026-11-03 内容型项目实录：健康检查提示失败但实际启动中 | 失败甄别：进程存活 → 自动延长观察 60s（12×5s）；延长通过=成功，仍失败/进程退出=真故障才回滚 |
| C3 | **"连上即成功"假象**：HTTP 连接成功但返回 500 | 早期版本漏洞 | 探活 fail-on-error 拒绝 4xx/5xx，校验响应体内容 |
| C4 | **差异方向误判**：把"本地待发内容"当成"云端热修"（或反向），导致覆盖事故或误同步 | 2026-11-04 project-a：precheck 报 routes.py 差异，被保守解读为"云端领先"；实为本地新增 52 行 | 铁律 2 方向口诀 + 三重证据判定（体积/内容超集/md5）；**云端 mtime 不可信**（tar 发版会带本地 mtime 上云） |
| C5 | **FORCE 绕障**：检查失败就用 FORCE=1 硬闯 | 铁律 1 立法动机 | 铁律 1：FORCE 禁止自行使用；例行发版走 `DEPLOY_EXPECT_DIFFS`（计划时传入，进 manifest 指纹）；FORCE 台账必须记原因与用户确认 |
| C6 | **单文件管道部署**：`cat file | docker exec` 只更一个文件，旧引用残留 | 历史事故（v2 立法动机） | 铁律 7：严禁单文件管道部署，只走全量脚本 |
| C7 | **grep 陷阱导致的误判**：BSD grep `\|` 交替不生效 → 误判"排除项不存在/文件缺失" | 2026-11-04 三个会话同踩（gate-ops 维护/project-e 复核/project-c 接入） | mac-traps.md：交替匹配必须 `grep -E`；验证类操作误判前先怀疑工具 |

**自检命令**：判定方向前必跑 `diff` 拉云端实物比对；健康判定必须读进程状态 + 响应体。

## D 类 · 留痕缺失（做完了 → 没证据，下次踩坑）

| # | 场景 | 真实案例 | 规避闸门 |
|---|---|---|---|
| D1 | **发完忘台账**：发版成功但台账没写，下次会话不知道云端处于什么状态 | 2026-11-03 project-a：另一会话发版漏写台账，暴露"发完忘台账"失败模式 | 发版后记忆写入为八阶段固定步骤（不可跳过）；脚本自动打印台账行模板 |
| D2 | **声称已提交但文件漏了**：回执/汇报说"已 git 提交"，实际文件还在工作区未跟踪 | 2026-11-04 project-compose（5 文件）+ project-c（markers）连续两例 | 提交后必跑 `git status` 确认无本系统残留；`gateo-doctor --deep` 的归属漂移检测持续盯着 |
| D3 | **共享脚本改动未声明**：改了 deploy/doctor 等共享脚本但没在汇报/提交里说明，被他人提交打包后归属不明 | 2026-11-04：doctor 放宽被 project-d 收编、project-c 的 exclude 被 project-e 打包 | 共享脚本改动**立即单独提交**（改完不留工作区）；commit message 写明动机与受益项目 |
| D4 | **内容级变更零留痕**：数据库改了/批量生成了，备份名只存在于当次对话 | 2026-11-04 project-a 210 题发布游离于体系外 | data-change 剧本：`gateo_data_*` 品牌命名（可 glob 检索）+ 台账 `data:` 行强制 |
| D5 | **凭据经对话泄露**：验证凭据时 `echo $VAR` 把 IP/密钥路径打进工具输出 | 2026-11-04 project-f 接入实录（对方自曝） | 验证凭据用 `grep -c 'CRED_XXX'` 查存在性，**永远不 echo 变量值**；回执/档案/日志只见 `<server>` |
| D6 | **身份与依据不写**：回执不说自己审的是谁、依据是什么 | project-b 误配的伴生缺陷 | 回执第一行强制：`本次系统=<X> · 身份依据=用户指定/确认` |

**自检命令**：`bash scripts/gateo-doctor.sh --deep`——D1/D2/D6 全部可机器检测。

## E 类 · 并发冲突（多个 Agent 同时动手）

| # | 场景 | 真实案例 | 规避闸门 |
|---|---|---|---|
| E1 | **并发发版互相覆盖**：两个会话同时 deploy | 锁机制立法动机 | 发版锁：nonce + 15s 心跳 + 主机校验；锁 30 分钟未释放自动回收；拒绝并发，提示手动清锁流程 |
| E2 | **并行改同一份源码，归属不明** | 2026-11-04 多会话真实常态（gate-ops 仓库一天 8 个系统的接入提交交错） | 铁律 3：发版单写者；并行改源码允许但必须 git 管理 + 分段 commit；**发版前差异归属必须判定并记台账** |
| E3 | **双本地副本混用**：同一系统两份本地源码，改的不是发的那份 | 2026-11-04 project-compose：`02本地内容型项目/prod-sync` 与 `Desktop/内容型项目` 并存 | 档案 `LOCAL_APP_DIR` 唯一权威 + 旧副本在档案中标注废弃 |
| E4 | **一边部署一边修改**：备份后、覆盖前现场被写入 | 三重校验的现场指纹设计动机 | 现场指纹比对：备份时记录内容指纹，覆盖前重算，不一致即终止 |

## 使用建议

1. **接入培训**：新会话/新 agent 接入 gate-ops 时，把本手册作为铁律的"为什么"阅读材料
2. **新闸门设计**：任何新风险先归入 A-E 类，找同类既有闸门参考形态
3. **复盘对照**：出事故后先查本手册——已有闸门为什么没挡住（绕过/缺陷/未覆盖），再决定是修闸门还是加闸门
4. **一句话时代的口诀**：**"身份用户定，范围计划锁，方向证据判，动作留痕查，并发锁先行"**
